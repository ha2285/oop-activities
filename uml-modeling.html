GOAL

Turn a plain-English system into three connected UML views

You will be given a short description of an online food-ordering system, QuickBite. Working from that description, you will produce three deliverables that must stay consistent with one another:

  1. One use case diagram — who uses the system and what they can do.
  2. A sequence diagram for each use case — the step-by-step message flow that realises it.
  3. One class diagram — the classes, attributes, methods, and relationships behind it all.

Learning objectives

  • Extract actors and use cases from a requirements description.
  • Model dynamic behaviour with sequence diagrams (lifelines, messages, returns, fragments).
  • Derive a static class model from behaviour and check the three views agree.

The workflow

How the three views connect
Each arrow is also a consistency check: every use case needs a sequence diagram, and every lifeline/message in your sequence diagrams should map to a class/method in your class diagram.

THE SYSTEM

QuickBite — requirements brief

QuickBite is an online food-ordering service. Read it carefully; every actor and use case you need is hiding in this text.

A Customer creates an account and logs in. They browse restaurants and view a restaurant’s menu, then place an order by adding menu items to a cart and checking out. During checkout the system takes payment through an external Payment Gateway. After ordering, the customer can track the order’s status and, once it is delivered, rate the order.

A Restaurant receives new orders, confirms (or rejects) them, and updates the order status as the food is prepared. A Delivery Driver sees available deliveries, accepts one, and marks it as delivered. The system notifies the customer whenever the order status changes.

Your checklist

✓
Every actor from the scenario appears (human and external systems like the Payment Gateway).
✓
You marked which actor is primary (initiates) vs supporting for each use case.
✓
4–6 use cases, each a goal (a verb phrase), all inside the system boundary.
✓
At least one «include» (e.g. Place Order includes Make Payment) with the arrow pointing to the included case.
✓
At least one «extend» (e.g. Rate Order extends after delivery) with the arrow pointing to the base case.
✓
No implementation detail (no “loop through cart”, no database tables) — only user-visible goals.
Common mistakes: making use cases too tiny (each button click is not a use case); drawing arrows to imply order (use case diagrams have no sequence); forgetting the external Payment Gateway is an actor.
PART 2 · SEQUENCE DIAGRAMS

One sequence diagram for each use case

A sequence diagram shows the objects that collaborate to carry out a use case and the messages they exchange, top to bottom in time.

Notation you’ll use

  • Lifelines — a box at the top (an actor or an :Object) with a dashed line down.
  • Activation bar — the thin rectangle while an object is doing work.
  • Message — solid arrow with a filled head (a method call).
  • Return — dashed arrow back (the result).
  • Fragments — alt (choice), opt (optional), loop (repeat) in a labelled box.

✓
There is exactly one sequence diagram per use case in your set.
✓

✓
Messages are labelled like method calls (placeOrder(cart), charge(total)) with at least one return.
✓
You used a fragment (alt/opt/loop) wherever the flow branches or repeats (e.g. payment success vs failure).
✓
You noted the objects that appear here — they will become classes in Part 3.
Tip: keep a :Controller/:Service object between the actor and the domain objects — it keeps each diagram clean and mirrors real designs.
PART 3 · CLASS DIAGRAM

The classes behind the behaviour

Derive the static structure from your scenario and sequence diagrams, then connect the classes with relationships.

How to derive it

  • Nouns → classes/attributes. “Customer places an order of menu items” ⇒ classes Order, MenuItem; data like price/quantity ⇒ attributes.
  • Messages → methods. Every message arriving at a lifeline in Part 2 is a method on that class (e.g. Order.addItem(), Payment.charge()).
  • Relationships → associations. Add multiplicities (1, 0..1, *, 1..*) and use aggregation/composition or inheritance where they fit.

Notation you’ll use

Class box, association, multiplicity, composition, inheritance

Worked mini-example (coffee shop)

Your checklist

✓
Every lifeline object from your sequence diagrams is a class here (and vice-versa — no orphan classes).
✓
Each class has meaningful attributes (data) and methods (from the messages in Part 2).
✓
Associations have multiplicities (e.g. a Customer has * Orders; an Order has 1..* OrderLines).
✓
You used composition/aggregation where a whole owns its parts, and inheritance only if a real “is-a” exists.
✓
Consistency check passed: every use case → a sequence diagram → classes & methods that all appear here.
